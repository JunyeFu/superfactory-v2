# v2.0设备进程、Native网关与部署设计

2026-10-26。**仅设计，v1验收优先，v2实施门关闭。** 本文与[结构化设计](设备进程网关与部署设计.json)、[接口／事务设计](接口与数据库事务设计.md)细化V2-02／03／04／10／11。没有创建设备脚本、网关、SQL迁移、云实例或新测试。

## 1. 选定的进程边界

保留现有Windows Native中的唯一Host／Engine。网关确定为Native内部受管actor；两台执行设备是两个独立Python进程，通过真实HTTPS云服务取令、报送回执和遥测。取消原定位中的独立gateway.py，普通Agent命名管道保持现有ExternalAgent身份，不承担网关授权。

Native的ProjectApiState已有Arc/Mutex持有Host及受管I/O线程（project_api.rs 33、484、492行），lib.rs 93行有setup注入点。沿用现有RenderBackend注入先例，新增仅供执行准备／自有设备启动和退出的窄运行时接口及一个Native实现，不建设通用设备插件框架。没有Native实际提供者时，standalone Host不能虚报准备或控制能力。

H01先登记真实Task，经worker在Host锁外冻结归档、完成C01、启动设备并核对boot。短事务建立原Engine及r0；r0实际发布确认后Task才completed并返回prepared。长期网关循环使用独立受管任务，不能堵住现有串行ProjectIoWork.run。网络、进程等待和SQLite I/O均在Host／Engine锁外。

新增DB15 device_boots、C19注册和C20退役；执行契约升为草案sf.execution/2.0-draft11，产品仍为0.1.0，旧Host API仍为0.1。

## 3. 设备动作、取消竞态与持久消息

每个设备使用一个状态写入循环，网络worker不在状态／SQLite事务内执行HTTP。私有运行目录按Host/session/device/boot隔离journal；其中只保存实际执行所需的boot状态、原取令请求、命令状态及待发送事件，不进入工程导出。

1. 发送C03前持久保存poll_request_id；包括empty在内的结果不可变。未知响应复发原请求，不创建另一个取令身份。
2. 收到命令先保存原typed payload与Accepted事件，再处理是否开始。Started状态与其不可变回执在同一SQLite事务提交后，才开始设备自身的实际单调计时。
3. C14的cloud_delivery.cancel_requested与Started由同一写入循环处理。取消先赢则记录cancelled_not_started；Started先赢则报告cancel_rejected_started并继续原动作，不能两者都成立。
4. 实际经过自身处理时长才生成Completed及device_reported_duration_ms。设备不写工程库存、资源或接受量，也不依据墙钟／预定动画补完成。
5. 回执和遥测共用boot/sequence的持久FIFO。云存储响应未知时只复发原payload；同存活进程网络恢复后续传原outbox，不重复动作。

设备意外退出不自动重启执行；原journal保留供核对。跨进程恢复正在执行的动作仍未实现或承诺，不能用重启新boot来绕过旧指令。正常退出命令走Native持有的私有stdin，仅在idle及出站结清后发送；仍有未知命令时保留窗口关闭阻塞。

## 4. Native网关的实际消费

|方向|消费者与提交边界|
|---|---|
|Host到云|H05取原work；锁外调用C02/C06/C09；拿到或查询到明确原结果后H06确认。未知结果不创建新的命令或attempt|
|云到Host|C05按原前沿取页，逐行调用H04/H07；实际Host准入与去重决定生产提交。准备期遥测可存云，不伪装已运行观测|
|云投影|TX06可合并待发布快照修订，但保留全部连续观察记录；网络ack不另产生生产事实|
|权限|Native setup注册内部Gateway上下文与精确设备/epoch；普通Agent、Renderer请求中的origin/grants不授予该身份|
|生命周期|准备Task、生产会话、网关任务和自有设备分别持有；面板退出或只读Task取消均不停止生产|

设计轮询间隔：设备遥测1000ms、取令／取消200ms、设备状态循环20ms、网关工作／入站100ms、本机观察100ms；单次HTTP超时5000ms。超时表示该请求结果未知，不表示命令未执行。这些参数不证明T8-Q04的2秒目标；原100个样本及同钟／有效保守上界要求保持。运行后新采样和有效期规则见下节，相关消费者尚未实现或验收。

### 4.1 V2-A10：运行后探测与有效期

采用Host发起的一次性观测请求ObservationProbe，复用现有C06快照、C03取令和C04遥测；不新增HTTP端点、逻辑表或单独消息通道。冻结策略增加observation_max_age_ms，演示profile取3000ms；Host探测间隔取1000ms。它与T8-Q04原100样本、p95≤2000ms是不同约束，后者保持原要求。

|步骤|生产者与契约|消费者规则|
|---|---|---|
|首次run|原Host建立单调锚点，为每个注册boot生成probe_id及原发起修订/时刻/到期时刻；ExecutionDeviceView.pending_observation_probe进入rN|prepared没有probe，设备状态待确认；首次回应前不新派工，也不为等待再重置报告时钟|
|发布与取令|C06发布同源快照；C03在同一次事务读取该boot的已发布probe，并保存到原poll结果|旧poll重发仍返回旧command/empty与旧probe；新poll才读取新头。忙碌/停止接单设备继续poll，accept_commands=false只取probe，不领取加工命令|
|新采样|设备第一次看到该boot/probe后，在单写者循环采当前状态，生成新sequence和不可变outbox行|按boot/probe唯一；不能给旧遥测补上新probe_id，重复probe复发原行，不重新采样冒充同一次回应|
|Host准入|H07核对原活跃Host登记的session/epoch/boot/probe及实际接纳时刻；HostObservedDevice保存原probe|仅未消费且actual_host_now严格早于expires才更新资格；设备或云时间不参与加减，普通请求不能注入Host发起时刻|
|原期限|expires=issued_at_host_ms+冻结max_age；在观察时点T，状态年龄保守上界为T-issued_at_host_ms|不能用received_at+max_age续期；同receipt重复返回原接纳，新sequence复用已消费probe也不更新资格|
|后续探测|每boot最多一个待答probe；已回答且距上次发起至少1000ms，或原probe到期，才发下一请求|新的请求等待中，上一有效回应可按原期限继续有效；云端不生成或延长Host期限|
|到期与重连|Host驱动器先处理已到期设备资格，再做新派工/发布决策；记录device状态变化|旧prepared消息、旧云头、旧poll或断连补发均不能续期；已发布/已开始工作仍保留原命令、物料与资源义务|

例如probe在Host 1000ms发起、4000ms到期，1700ms接纳：3500ms的年龄上界是2500ms；4000ms即过期。2900ms重发同回应仍在4000ms过期，不能延至5900ms。4200ms才收到的原回应只保留云端查询，不能恢复资格。

不再需要把C05游标跳到“运行开始之后”来猜消息新旧。prepared原始遥测可保留且不提交运行准入；run后的无probe／过期回应不能进入资格投影。生产Started／Completed继续按原身份和依赖处理，不能因已经看见较大遥测sequence就丢弃较小合法生产回执。网关只在Host已接管待依赖回执后推进原始流位置，不删除原回执或另建执行尝试。

资格到期需要成为真实Host状态边界，即使没有新网络消息也在下一次派工前处理；读接口不推进Engine或制造到期记录。固定R/F/T的设备历史保存发起、准入及失效状态。Renderer、普通Agent与报告只消费当时Host结论，不按本机Date.now把历史快照重判为在线；云旧头必须显示其观察时点。

pause/resume不重置锚点或期限；终态停止新探测，迟到消息不能复活会话。原Engine丢失的Host只能只读，不用归档probe恢复控制。探测发起还可作为原T8-Q04有效因果样本的发送前计时点，但须另有同钟的真实正确帧确认，按[时延证据规则](外部时钟与结果投影设计.md#52-原2秒目标如何取有效证据)保留原100样本。这个协议上界依赖设备确实收到probe后重新采样；当前软件设备实现仍待验证，真实物理状态／有效加工证据继续按原来源声明。

## 5. 两设备执行与采集负载分别验收

DatasetDescriptor和DB04增加purpose。实际source_mode仍区分software_in_loop、physical_device、generated_load；purpose说明数据的消费者，不能把软件设备写成真机。

|purpose|身份与入口|验收对象|
|---|---|---|
|execution|C01生成有session的dataset；两设备C19；C04 execution遥测／receipt进入C05及Host准入|完整演示产线、外部时钟、改派和生产接受结果|
|telemetry_only|部署配置预置独立dataset与10个绑定；session/epoch/active_command为null，accept_new_work=false；C04仅存采集|10个独立采集进程，各1条/秒持续1800秒，预定18000条；记录实际遗漏和到达分布|
|generated_load|独立generated_load dataset；C11批量写合成行|100万事件、查询和聚合各30次；不能替代1800秒的真实采集|

TelemetryObservation拆为明确的execution／telemetry_only变体，H07只接受前者。仅采集返回host_admission_state=not_applicable；它不注册执行boot、不取生产命令、不占生产slot、不进入生产接受量。两类非执行dataset由部署配置初始化，不新增通用数据集管理后台。

## 6. 部署及版本决定到哪一步

部署形态为一个Rust HTTP服务＋托管PostgreSQL，PaaS提供HTTPS入口；Native与设备只做出站连接。角色使用固定作用域凭据，服务端／Native私有配置持有密钥，devices.demo.json只存非密钥profile。网关固定云地址与typed路径；Renderer不接受或转发任意URL、方法、token，跨主机重定向不能携带凭据。

本机只读命令确认Python 3.14.7／stdlib SQLite 3.53.1、rustc 1.97.0。它们是本机现状，不证明交付包自带解释器。V2-10的随包参考已选官方CPython3.14.9及实际portable复制；模块、来源／权利及发现方式仍须按实际包验证；解释器缺失应使准备明确失败，不能返回空设备的prepared。

设计依赖候选为axum 0.8.9（Tokio HTTP路由）、reqwest 0.13.5（异步JSON／query／rustls客户端）、tokio-postgres 0.7.18（with-serde_json-1）。这些版本与特性已核对官方文档，未安装、解析锁文件或编译验证；tokio-postgres的TLS需外部提供者，实际托管PG连接方式仍待固定。[axum文档](https://docs.rs/axum/0.8.9/axum/)、[reqwest特性](https://docs.rs/reqwest/0.13.5/reqwest/#optional-features)、[PostgreSQL驱动TLS与特性](https://docs.rs/tokio-postgres/0.7.18/tokio_postgres/#ssltls-support)。

[托管与交付设计](托管部署配置与交付闭包设计.md)已给出Render/PG18/10GB、验证TLS和预算公式作为参考；实际账号／资源、小版本、锁解析／连接与账单仍未取得。本轮无云资源、服务启动或端口占用；本机localhost也不算云验收。实施时再按全局端口注册表分配真实端口，实际付费操作消费用户当时有效授权。
