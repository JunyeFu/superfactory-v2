## 2. V2-A02：逻辑工单不变，选择时才绑定设备

每个任务周期和路线步骤仍对应一个logical_job_id，使用现有稳定身份的语义。会话冻结时保存该逻辑工单的候选绑定集合；集合中的每项包含实际设备、精确模块／工艺、执行容量资源、物料端口和位置、角色资源及已解析阶段模型。

两台设备是同一项工作的候选执行者，不是两项独立生产工作。编译候选不能把它们都加入普通jobs队列，否则六件投入可能变成十二个作业的生产尝试。

|冻结内容|选择前可以改变的内容|命令发布后必须保留的内容|
|---|---|---|
|会话输入、目标、工单身份、允许候选集合、各候选的工艺／端口／资源映射|在允许集合内按当前可用性、资源和预计完成时间选择候选；展示尚未承诺的预计分配|本次CommandId、attempt、设备、阶段token、动作参数和原绑定；不得用新设备覆盖旧命令历史|

候选工艺必须通过现有OperationDefinition、公开参数、单位、资源、日历及material映射检查。Scenario.parameter_overrides当前要求事先降入冻结执行定义，不能用未解析override临时改设备速度。A／B可以有不同的已声明节拍，但不能因此改变投入／产出类型、单位或物料身份规则。

在命令前尚未形成实际执行的逻辑工单，由新的执行投影显示“待分配／已预留”等状态；不捏造一个已绑定的JobExecutionRef。绑定提交后，内部作业状态保存该次真实执行设备身份并保持不变；外部通过独立BoundExecutionJobSnapshot呈现已证实字段，不直接将缺测量的旧有效工时字段解释为实际设备工时。新增投影不改变旧RunResult对历史JobState的解释。

## 3. V2-A03：预留、设备开始、业务完成分开

当前派工把物料取得、资源占用及虚拟阶段开始合在一次内部转换中。v2需要在同一个Engine内增加外部准入状态，不能让云数据库或网关保管另一份库存。

|阶段|物料／资源行为|设备与指令行为|
|---|---|---|
|queued|未取料、未预留；仍是同一个逻辑工单|可重新选择未承诺候选|
|reserved|Engine内部预留精确物品数量及容量；扣减可用量但不改物品holder／lifecycle|建立唯一命令标识和阶段token，尚未发布可安全撤回|
|published／accepted|保持预留，不以网络超时释放|原命令已对设备可见或已接受；只能查询／核对同一次尝试|
|device_started|一次Engine事务将预留转换为Stock.take及原Job／资源占用；保留原拆分和allocation身份规则|设备、Job、阶段及命令绑定成为实际执行身份|
|device_completed|核对原会话／设备／token／顺序后进入原工艺完成链|设备完成事实可见，但尚不能把它直接计成终点接受量|
|business_effect_committed／output_wait|沿原produce／transfer／acceptance处理；遵守输出满库、质量及保持资源要求|设备命令完成与生产接受分别显示|
|accepted|由原接受规则确认结果|报告引用实际物品、接受事件及命令关系|

预留必须参与Stock.plan和资源容量判断，避免两条待接受命令同时拿到同一件原料。它是现有Stock中的一种受控占用，不是云端库存。撤回未发布命令、或得到明确cancelled_not_started回执，才释放相关预留；已经开始或结果未知时不能回滚已发生物料变化。

有效Started只提交一次take；有效Completed只提交一次工艺结果。重复事件返回原结果。字段或状态不匹配时拒绝业务提交并保留原因，不通过调用私有finish“补齐”状态。

## 4. V2-A05：改派资格与竞态

|工作状态|是否可直接改派|必须采取的动作|
|---|---|---|
|尚未预留／发布|可以|在冻结的合法集合重新选设备，逻辑工单不变|
|已经预留但未发布|可以|Engine释放该次预留并重新选择，保留尝试归属|
|已发布或已接受但未确认开始|不可以直接改派|取得原命令撤回或cancelled_not_started的确定结果，才能释放预留、生成下一attempt|
|已开始|不可以|非抢占工序继续原设备；异常进入明确处置，不在另一设备重做|
|结果未知|不可以|保留预留／已提交状态，查询原命令与原设备，不能把失联当取消|
|已完成但待输出／接受|不可以|继续原输出和接受链，不再发送加工命令|

停用A的含义是“不再向A派新工作”；已经在A开始的工作仍归原命令。撤回与设备开始竞态时，只有明确“未开始已撤回”才允许改派；已经开始或不能确认时原尝试保留。下一尝试使用新的CommandId和attempt，但保留同一logical_job_id；旧回执不能写入新尝试。

## 5. V2-A04：时钟与结果投影的后续细化

方向已经收敛为：外部会话以Host单调经过时间及入站事件序列为准，设备时间保留为观测数据；虚拟本地运行继续使用原事件队列跳时。外部驱动器在没有新外部事件时等待，不调用旧run_worker空转，也不直接跳到未来模型工时结束点。

模型声明10秒只用于预测、选择候选及展示依据。没有有效完成回执时，经过10秒不产生输出，经过原观察窗末也不伪造Completed。后到事件不能凭设备过去的时间戳改写已经提交的历史；同毫秒事件按Host接收序列保留因果，不假装能够提前知道稍后到达的停用通知。

下列三项已由[外部时钟与结果投影设计](外部时钟与结果投影设计.md)形成设计规则，schema与事务草案见[接口设计](接口与数据库事务设计.md)，仍需实际生成契约验证与v1最终接点核对，**不把DEC-03标成可编码完成**：

1. 截止仅停止新派工并保留不可变快照，已准入工作继续核对；独立外部驱动器不能套原Engine.end自动完成语义。
2. 使用独立ExecutionSnapshot组合未绑定工单、预留和真实业务事实；旧RunResult及其完整计算／比较校验保持原义。
3. 模型名义工时、Host确认占用、设备自报时长分开；缺测量的物理有效工时为null，不能把网络确认区间填入PhaseWorkInterval。

当前[reporting/evaluation.rs](../../packages/reporting/src/evaluation.rs)第145—161行已区分有进度却缺有效工作区间的未知情况；[时间轴投影](../../apps/planner/src/features/timeline/projection.ts)第149—156行会将该区间直接显示为“实际有效工作”，[CSV输出](../../packages/reporting/src/evaluation_rows.rs)第395行也消费同一字段。因此不能为了复用显示而把Host收报区间填入phase_work_intervals；下一步应核对未知指标的实际输出字段，并完成来源分明的执行投影。

这些选择保留执行反馈要求，并明确时钟和结果定义。新增Host操作／DTO及数据库事务已形成设计草案，当前继续核对实际字段消费者及人工恢复边界；任何接点试证仍在v1验收完成后进行。

## 6. 一条独立有限预期

设计案例使用单工序、两台容量为1的设备、同一合法工艺、6件原料和6件合格接受目标。A／B名义周期10秒／15秒；输入端映射到明确的共同原料位置，输出端映射到可接收的目标位置。具体工程、设备、端口和资源ID待v1最终随包候选选定，不编造它们已存在。

下面是设计注入事件，不是网络实测：

- 正常案例在Host时间0确认A执行W1、B执行W2；10秒A完成并开始W3，15秒B完成并开始W4，20秒A完成并开始W5；30秒两个完成均已处理后，W6选择预计更早完成的A，40秒最终完成。结果为6次实际工作、6件接受，不能生成12项生产工作。
- 变化案例在6秒明确A停止接单，W1仍在A执行并于10秒完成；B在15秒完成W2，此后依次执行尚未开始的W3至W6，直到75秒完成。已开始W1不转给B，剩余工作保持各自逻辑身份。
- 上述理想时点仅供算法设计核对。真实云端案例按实际回执和来源记录时间；不能把40／75秒手算当作演示实测成绩。

输入质量、输出Released、类型／单位及接受目的地必须在模型中明确。仅有六个Completed命令而缺输出移交，不满足六件接受。
