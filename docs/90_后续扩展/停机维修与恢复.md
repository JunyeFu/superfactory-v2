# 停机、维修、恢复与在制处置

范围：**后续储备设计，当前首版不实现停机、维修与恢复**。首版按[交付基线](../00_项目基线/首版交付基线.md)及[S01-01产品边界](../00_项目基线/用户任务与产品边界.md)执行；本页保留该扩展的设计，不作为当前首版能力声明。
状态：业务设计。处理方案里明确安排的维护窗口和故障注入，不自行生成故障率、MTBF、MTTR或随机良率。设备图中的故障素材不触发实际故障；维修完成也不自动恢复合格生产。

## 完整工作与状态

安排停机/注入事件→阻止新开工→处理当前作业及物品→等待维修资源/备件→维修→复核/重新投用→明确放行→恢复原作业或新作业。每一步显示条件和当前持有者，不能用一个“修好了”按钮同时重置设备、退回材料并生成合格件。

|状态|生产与维修含义|
|---|---|
|available/running|按正常工序规则；是否允许新开工由需求、阶段和准备共同决定|
|quiescing|已请求停新作业，当前作业按finish_current完成到认可停机点|
|suspended|按明确规则保存有效进度及在制，等待处置或维修|
|maintenance|维修任务排他使用设备，消耗实际备件/工具/人员和时间|
|requalifying|维修完成，但指定复核或投用条件尚未结束|
|awaiting_release|缺决定/结果/必要条件，不自动可生产|

这些是设备业务状态；物品仍有独立位置/持有、生命周期、质量和订单关联。操作员、维修人员和质量负责人是任务责任，不要求本轮新增账户权限系统。

## 用户明确选择哪种停法

**finish_current：**到停机请求时不再接新作业；当前作业按规则做到认可停机点，包括不能丢下的在制/输出移交。若接收满，停机可能晚于计划，报告实际起始与原因。现场是否允许作业继续由输入条件决定，不由软件判断。

**pause_resume：**当前阶段明确可保留并继续，有效进度冻结；是否能保留在制/夹具及作业条件另行声明。维修后还要复核对应条件，才续剩余有效工作；不是重新执行整道工序或无条件续上。

**abort_disposition：**不能继续时终止本次尝试，按明确任务将物品移至待判/隔离或其他合法位置。已投入材料不自动退回库存；继续处理、返工或拆解需要自己的条件与任务。保留身份/组成和订单缺口，不自动生成替代产量。

已知不可中断阶段遇到预定硬停窗口时，在调度前找足够连续区间；不够则等窗口之后。计划允许finish_current时才可推迟维修。未知/未声明的突发中断处置停在待决定，不替用户选最方便的恢复方式。显式扩展以外，旧样例仍无维修事件。

## 排他使用与恢复关联分开

暂停作业可保留物品/夹具，但不能一边独占机床当前使用权、一边要求维修任务取得同一机床。显式维修停机成立后，生产有效使用停止；等备件/人员时设备不可生产，当前活动使用者可为空，维修开始才交给维修任务；原作业保留resume_ref恢复关联，防止其他生产任务抢走它。这个关联不重复计设备容量，也不自动释放在制。

维修是否允许在制保留在机上是必要输入。允许时，物品仍由原作业持有；设备当前使用者是维修任务，生产进度不动。禁止时，先完成声明转移/处置，物品进入有限接收位置后维修才可开始；位置满就保持等待，不能删物品腾机器。

维修需要的人员、工具、服务和备件都引用工程已有对象。备件是消耗物品，投入后不因维修结束自动补回；工具是复用资源。维修人工作量与设备停机跨度分开，例如等待备件20秒不是维修员已经工作20秒。所有资源共享日历，不因进入维修分组再复制一名工人。

## 修复、复核和允许生产

维修结果说明目标、原故障与处置、所用任务/备件及完成时点。恢复还需相应投用包/服务、工艺家族、夹具和专业成果范围。工艺参数被改动、工具被替换或首件要求被触发时，列受影响绑定和必要复核，不能把设备“通电”当成全部专业条件有效。

复核PASS只有在所需决定完成后才放行；FAIL或缺值保持awaiting_release，下一修复任务需明确安排。当前可配置预设模拟结果或实际专业结果，来源必须显示；预设PASS不证明现场设备性能。

恢复原作业保留原物品ID、已做有效进度和资源规则；恢复新作业重新核对齐套。原在制不适合续做时，进入处置而不是复位到开工库存。整厂“复位彩排”是从方案输入重新开始观看，与维修后的继续生产完全不同。

## 用户界面和真实反馈

设备详情的维护区设置任务范围、停法、是否保留在制、人员/备件、复核和放行；生产画面显示停新单、冻结、维修、复核及等待原因。全厂时间轴同时显示设备不可生产、维修人实际占用、备件到料及原作业恢复。

点击恢复条件展开：原作业在哪里/还剩什么，维修已做什么，哪些专业/服务条件待复核，是否有足够资源完成下一阶段。未知恢复日期保持未知，不从故障图估一个倒计时。该扩展的首个实现使用方案输入里的声明事件；运行内请求停机/处置需界面和共同引擎实现之后再开放。

## 有限贯通案例

- 30秒请求finish_current；原作业60秒有效完成，但输出80秒才接收。维修80—100、复核100—110，新作业110—170。设备没有同时生产和维修。
- 作业0—30有效，30秒暂停；维修人40秒才可用，备件50秒到；维修50—70、复核70—80，80—110续剩余30秒。总有效加工60秒，本工序输出110秒才接受，不自动等于客户订单完成。
- 不允许保留在制时，30—35秒移交隔离，再安排维修与复核；80—140做第二件。第一件仍保留待处置身份，不自动补产或退回输入。
- 复核失败或缺中断策略时，完整完成时刻为空；已有进度/在制仍可见，不能用0秒或成功灯补齐。

参数全部为自建示例，具体输入/预期见[路径与维修](../../scenarios/路径与维修/README.md)。本轮补的是产品业务，不是现场维修授权、机器安全控制或实际工业故障数据。
