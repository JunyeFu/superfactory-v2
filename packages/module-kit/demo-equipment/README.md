所有秒数、容量和胶带用量都是自建演示输入，不是从AI图片或实际工业设备测得。每次作业只占用一个设备实例；修改规则/参数进入新方案，正在运行的作业不偷偷换版本。

## 同一个外观可以属于不同的东西

`assembly.glb`也可供既有`community.manual-assembly@0.1.0`复用。它只需要壳体1＋PCB1、装配人员1，工时60秒；与四螺钉／40秒版本保持不同定义ID、名称、参数和端口。人工装配可以复用台架几何，不能照搬自动紧固动作。更换外观不改变配方，显示名改变也不生成新的业务身份；不同用途并存用不同定义ID，同一定义的演进用新版本。

## 动作如何跟业务走

正式表现读取共同引擎快照中的实例ID、定义版本、状态、阶段、有效进度、等待原因、物品持有者和端口／资源绑定。推进、暂停、速度与单步由共同仿真时钟决定。设备视图和流水线视图读取同一状态。外观区间只解释当前进度，不自行扣库存、产生物品或决定质量。

- 装配台的上料／紧固／回位区间按既有40秒working阶段的20%／60%／20%显示。这是表现划分，保持原配方、工时及人员规则；不能因此增加三次业务提交。
- 机器人示意阶段为到位2秒、闭爪1秒、带料移动5秒、放料1秒、回位3秒。来源物品先预留，3秒闭爪完成后才转到机器人持有；目的空间不足时停在放料前，保持闭爪和原物品；等待不计入有效工作秒数。放料开始时预留目的接收容量，完成时把同一物品移交一次，随后空载回位。允许额外等待，所以12秒是无等待作业时间。
- 输送机开工时把原物品从来源转到设备持有。4秒后若目的不可接受，停带并保留在出口；接受后移交一次。更改带面纹理或播放速度不能改变这4秒配置。
- 检验台保持原定义的质量输入与分流规则。灯环只是检查状态提示；缺质量结果不能靠动画结束默认合格。未知结果或出口满的等待由原行为决定。
- 封箱机开工前预留原包件与0.6m胶带，进箱时转移原包件持有者；第6秒封箱完成才扣除预留胶带并设置同一包件的closure为sealed；第8秒若出口可接受则移交。出口阻塞保持封箱结果，不重新耗胶带。
- 托盘槽位只关联已有包件ID。包件的唯一位置仍为绑定库位，槽位表示这个库位中的载具归属；不能再把它们重复计入另一份托盘库存。载具运输后按共同物流规则更新位置。

候选设备修改cycle_seconds时，阶段按声明ratio同比缩放；上表时点是默认参数下的预期。封箱开工所需胶带取配置的tape_per_carton，不把0.6m写死为另一个判断条件。

当前24秒视频仍是主轴和夹爪的隔离动作预览，与上述正式业务节拍无关。现有GLB中的工件、纸箱和十二箱堆均为示例几何；业务接入时默认隐藏，依据真实实例生成或绑定，同一物品在两处不得同时作为现有库存显示。

## 3D制作与接手的最低要求

详细档以既有AI设备/产线预览为视觉参考，模型必须有可观察的背面与底部，支持自由旋转。简化档只简化几何／材质，区域档聚合显示，三档共用业务对象和状态。

活动部件必须在原始GLB中保留明确名字、层级与动作参数。检查入口读取原始节点，不把显示时合批的网格名当编辑部件ID。同名重复节点用数量／成员定位，不能只找到一个名字就声称完成全部绑定。各业务端口还须有显式素材锚点；当前仅明确端口角色，锚点位置未制作，列入接入剩余工作。

机器人最低动作范围是固定底座、六个独立关节及示意限位、明确取放目标与可插值的名义关节姿态、夹爪、货物挂接。当前固定任务由示意连杆运动学实现，通用示教编辑器仍待后续接入。工业逆运动学、动态规划和碰撞求解不在这份演示要求内。它也没有点胶能力；点胶须另建耗胶／路径／工时定义，即使复用同一机身外观。

模型使用米、Y向上；领域X/Y/Z高到表现坐标按`(x,y,z)→(x,z,-y)`转换。布局足迹与机器人运动范围必须单独采用，不能将静态网格包围盒当作真实设备尺寸或安全范围。现有资产许可待项目确认，暂为工作区试样引用；贡献包要收入包内路径和许可，当前文件不是可发布的模块包。

现有装配工件、封箱示例箱和托盘箱堆没有同源物品规格，不能直接串接为同一物品的正式外观。业务接入必须按工程的物品类型／版本／规格采用同一份物品资产，各工位只改变位置、状态或指定工艺属性。固定示例几何先隐藏；真实包件随同一ID移动，不在每台设备里重新用另一组尺寸生成。具体锚点坐标、示教姿态、参数支持范围和正式快照字段仍待S04/S06明确。

## 九类如何覆盖与组成产线

九类是一份完整工程的角色划分，不要求每台机器复制九份定义。[机器可读责任表](equipment.design.json)逐类保留使用处和缺项：devices为五台固定设备，resources为人员与托盘，media为六份可共享外观，items/operations/tasks为相应物品、配方和任务；templates组合布局，transport按需承担厂际交付，professional提供认可的纸包装成果。

L03局部实现已按装配→机器人→输送→检验放行→输送→装箱→封箱→托盘贯通，并接入返工/复检与隔离。**检验输出仍是assembly，封箱输入已经是package，中间显式执行既有`community.carton-pack@0.1.0`的15秒装箱规则与packer资源。**PK01复用台架几何、使用不同定义与动作。物品/胶带定义、closure、库位容量、四个人员角色、供料及固定任务位置均已进入局部输入；正式公共类型、可编辑锚点与工程格式仍需在S06认可。

## 检查入口

在软件工程根目录执行，无新增依赖：

```powershell
python packages/module-kit/demo-equipment/check_requirements.py
```

检查共同类别载荷、定义／版本引用、参数和端口绑定、阶段覆盖、六份实际GLB的节点数量／已有动作参数，以及七个有限规格预期。输出`static_design_and_actual_glb_binding_checks`，只读检查，不改这些设计用例的`actual_result`，不注册catalog。[八项实际L03业务检查](../../../tools/3d-proof/output/line-business-checks.json)另记录真实局部执行结果；正式产品消费者接入仍须独立验证。
