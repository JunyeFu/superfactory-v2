# 真实业务规则的自建演练

不是企业案例或真实软件执行。除明确运输外工位间移交瞬时；多订单资源在0—240秒可用，质量案例资源在0—120秒可用。普通工位接收容量分别为4/3，待判与隔离容量另列；小车装载在示例中为0秒。全部尺寸、工时、交期和决定时点为自建输入，实际结果始终null；有限复算用于核对设计逻辑。[输入](business-inputs.design.json)与[精确预期](expected-business.design.json)分别保存。

## 1 多订单、换单与客户接收

产品A/B各2件，共用4壳体、4PCB、16紧固件和4空盒；PCB2片初始、2片100秒到达。设备初始已准备A家族，A→B换单15秒、B→A25秒，占装配台及W-A；装配30、检查10、包装10秒，W-B共用检查/包装。所有检验PASS，初始无成品。产品差异为已声明工艺/标签家族，不由图像自动推断兼容。

订单A需客户接受2件不晚于160秒，B需2件不晚于200秒；不接受部分交付。共用T1载量2，仅120/180秒发运，去程20秒、卸载5秒、返程20秒，接收容量4。客户接受发生在卸载结束，不在包装完成时。

|决定|包装结束A/B|客户接受A/B|订单迟延A/B|W-A占用|
|---|---|---|---|---|
|A先做|80/180秒|145/205秒|0/5秒|135秒|
|B先做|180/95秒|205/145秒|45/0秒|160秒|

两方案都205秒交完；业务取舍不同。A先做换单1次，B先做2次；即使后者优先B，也不能称总体最优。第一趟车165秒可再用，第二趟225秒可再用；205秒接收完成不等于运输资源全部空闲。

## 2 班次和阶段资源

机器可用0—100秒；W-C可用0—20、40—60秒；单件上料5、自动30、下料5。阶段为non_preemptive。上料0—5、自动5—35、等待人员35—40、下料40—45。机器全程持有，人员只占10秒；有效过程40秒、历时45秒、等待5秒。

没有自动推断加班，也不把35秒当完工。机床/人员日历与图片播放速度无关。

## 3 待判移交、复检和报废

3套初始齐套，3空盒；W-A装配每件20秒，共0—60；W-Q检查10秒；独立W-P包装10秒。第1件PASS，30—40包装。第2件50秒FAIL，60—75返工，75—85复检再次FAIL，进入容量1隔离位；100秒按预设处置报废。第3件70秒UNKNOWN，移入容量1待判位后释放检查员；90秒预设人工放行，90—100包装。

80秒第3件仍待判，第2件正在复检，两者都不能算成品。最终2成品、1空盒、1报废装配体，订单目标3仍缺1，完整订单时刻null。没有自动补产、回收零件或虚构质量准确率。人工放行与报废是模拟预设决定，不是正在运行的软件按钮。

## 4 从粗规则到细规则

相同班次下，“单阶段40秒，全程需W-C”找不到连续40秒窗口；明确上料5/自动30/下料5后可在45秒完成。改变的是人员需求和行为规则，不能宣传为仅换外观就提高产能。若只换图片，业务预期必须相同。

这说明渐进建模的价值：有能力把粗假设修正为明确业务，而不是承诺模型越细产量必然越高。

## 复算与后续验证

运行`python 复算业务案例.py`生成六个变体预期，核对资源不重叠、未来PCB不提前消耗、客户接收、班次内人员占用和空实际结果。它按本例有限步骤计算，没有通用排程内核。后续P1-04/P1-05/P2-05/P2-06按真实产品结果核对，再生成可用于比赛提交的录屏与工程包。

## S03-02 规则边界复核

运行 `python scenarios/真实业务设计/复核业务规则.py`（从软件工程根目录）核对[6个冻结边界输入/预期](business-rule-boundaries.design.json)：质量/预留重叠与取得失败、部分接受、取消后的实物保留、待判容量/资源释放、确定优先序和受阻结果只移交一次。脚本还在内存复算原6例并与原expected-business.design.json比较，不改写冻结预期；输出[有限复核结果](business-rule-verification.json)，不代表生产引擎执行。

两订单案例allow_partial=false且每次完整发运2件，原145/205秒订单接受不变；quality_pending_and_scrap是旧目标需求模式，不补造订单flag。当前业务语义取[订单规则](../../docs/01_业务需求/订单工艺与物料分配.md)和[异常出口](../../docs/01_业务需求/换单班次与质量处置.md#s03-02-异常与恢复出口)。
